# Stuck Talos reboots during upgrade: drop `rebootMode`, contain (not fix) with `waitForVolumeDetach`

A routine tuppr-driven Talos upgrade (v1.13.8 → v1.13.9) across the 3-node control plane took down ~3 hours of live debugging and two manual physical power cycles. `ser8c` and `ser8a` each independently hit the same pattern: tuppr cordoned and drained the node, the node logged `[talos] upgrade completed successfully: exit_code=0` (the new installer image genuinely written to disk), and then the node simply never rebooted — no new dmesg entries, uptime kept climbing, kubelet/containerd kept running on the old kernel indefinitely. A manual `talosctl reboot` retry then hung forever on `task unmountPodMounts (1/1): unmounting .../rook-ceph.rbd.csi.ceph.com/.../globalmount/...` — a kernel-level Ceph RBD unmount that never completed. In both cases the drain step immediately prior had a slow/stuck pod to evict (`omada` on `ser8c`, `victoria-logs-0` on `ser8a`). Only a physical power cycle broke the deadlock each time. Both nodes' rook-ceph OSDs were separately found wedged on stuck internal `watch unwatch` ops around the same window.

`spec.policy.rebootMode: powercycle` had been set on the `TalosUpgrade` CR since it was first added to this repo (May 2026), with no explanation recorded anywhere, and was the initial suspect: the hypothesis was that an ACPI power-cycle request wasn't being reliably honored on this Beelink SER8 hardware. That hypothesis doesn't survive contact with how Talos's shutdown sequence actually works. `rebootMode` only selects the final reset mechanism (kexec syscall vs. an actual firmware/ACPI power cycle); the `unmount` phase — including the exact `unmountPodMounts` task both nodes hung on — runs identically before that mechanism is ever chosen, for every value of `rebootMode`. The manual `talosctl reboot` retry hanging on the same task, with no upgrade in flight, confirms this: the hang is upstream of anything reboot-mode-specific.

Before dropping it, we checked whether `powercycle` might be an informed choice worth keeping anyway — onedr0p's own `home-ops` cluster (a major home-operations reference, and onedr0p is a heavy contributor to tuppr itself, 229 commits on the repo) carries the same setting. Git blame on his `talosupgrade.yaml` traces it to the literal first commit that deployed tuppr to his cluster (`9cb4058`, 2025-09-19, `"chore: deploy tuppr for testing talos upgrades"`), with no explanation there or in any of the ~15 subsequent commits that touched the file since. That undercuts rather than supports "he must have a reason": it reads as a value set once, early, while actively shaking out a brand-new tool — a reasonable moment to default to the more forceful mode — that then rode along unexamined in both repos for a year. Two independent homelabs carrying the same unexplained setting is evidence of copy-forward inertia, not convergent expert judgement.

Keeping it is not free, either: `powercycle` goes through a full firmware POST/BIOS boot every reboot instead of kexec jumping straight to the new kernel — real, cumulative downtime across 3 nodes on every future upgrade — and it carries its own documented failure class on other hardware (an infinite-reboot loop reported on OVH's PXE-chained boot setup). Nothing says that applies here, but nothing says it doesn't either; it's an unverified assumption in the *other* direction. tuppr's own docs describe `powercycle` as a fallback "for nodes that don't reboot cleanly," not a proactive default. We dropped it, falling back to tuppr's own default of `default`.

### What's actually happening, and why `waitForVolumeDetach` doesn't fix it

The stuck-unmount symptom matches a specific, real Linux kernel bug: **CVE-2026-23047**, *"libceph: make calc_target() set t->paused, not just clear it"*. When an RBD client's connection to its OSD drops mid-operation and a linger (watch/unwatch — the mechanism backing an RBD mount's lock) request gets paused during that window, this bug can leave `rbd_dev->watch_mutex` held forever; any later `rbd unmap`/unmount hangs in uninterruptible (D) state, permanently, unkillable by anything short of a reboot of that node. `dmesg` from `ser8b` the night of the incident shows exactly the trigger condition — real OSD socket resets/reconnects (`osd0 socket closed`, `down` for 19 minutes, then `up`; `osd2` similarly) — the kind of connection churn a rolling upgrade produces across multiple nodes in a short window.

`spec.policy.waitForVolumeDetach` (default `false`) makes tuppr's drain step block on CSI volume detach *before* it hands off to `talosctl upgrade`/reboot, instead of letting Talos discover a not-yet-detached mount during its own shutdown sequence. We turned it on. **It does not prevent the deadlock** — CSI detach walks the same kernel `rbd unmap` path, so if the mutex is already stuck, the wait hangs too; nothing in Kubernetes or tuppr can free a kernel mutex. What it changes is where the hang surfaces: without it, Talos's `unmountPodMounts` task has no timeout of its own, so the node hangs silently and indefinitely — the only way to notice is watching uptime not climb, and the only way out is physical access. With it, the same hang happens inside tuppr's own reconciliation loop, bounded by `policy.timeout` (30m default), and shows up as the `TalosUpgrade` going `Failed` — visible, alertable, no physical intervention needed to *detect* it (a forced reboot of that one node is still needed to *clear* it). It also independently prevents the Multi-Attach cascade seen in the `victoria-logs-0` side-incident, by never letting Talos reboot ahead of a real CSI detach.

We checked whether the fix is imminent via a Talos kernel bump: it isn't. Talos deliberately tracks the 6.18 LTS branch (supported through December 2028) — mainline Linux has already moved past 6.19 and 7.0 (both non-LTS, both already EOL) to 7.1/7.2, and Talos has no reason to chase any of those. The fixing commit landed upstream for the short-lived 6.19 cycle and, as of the newest 6.18 LTS point release (6.18.45, 2026-08-19), has not been backported into the 6.18.y stable tree — no commit touching `calc_target`/libceph/rbd linger handling in that changelog. So there's no "just wait for the next Talos version" resolution; the bug is open-ended.

## Considered options

- **Keep `rebootMode: powercycle`, look elsewhere for the fix.** Rejected: no evidence it was ever load-bearing (including on onedr0p's own cluster, see above), tuppr's own guidance treats it as an opt-in escape hatch rather than a default, and it doesn't touch the phase where the hang actually occurred — plus it costs real reboot time on every upgrade going forward.
- **Just raise the drain/upgrade timeout.** Rejected: a longer timeout gives a stuck RBD unmount more time to resolve on its own, but the observed hang was not transient — it held for the rest of the live debugging session until a physical power cycle. A bigger number turns a 3-hour incident into a longer one, not a bounded one.
- **Switch rook-ceph's CSI mounter from kernel `krbd` to userspace `rbd-nbd`.** Not rejected, but deferred. This is the one option that would actually remove the vulnerable code path (the deadlock is in-kernel; `rbd-nbd` runs the client in userspace), rather than just bounding the blast radius. It's a cluster-wide storage-path change with its own performance and stability trade-offs — worth a dedicated investigation on its own, not a same-night decision.

## Consequences

- This does not fix the underlying kernel bug (CVE-2026-23047) or the rook-ceph OSD watch/unwatch churn that triggers it — it only bounds and surfaces the failure instead of leaving it silent and unbounded. The same class of stuck node can recur on any future upgrade that hits the same connection-churn timing; when it does, expect a `TalosUpgrade` `Failed` status after ~30 minutes rather than a silent hang, and expect that node to still need a manual forced reboot to actually clear.
- `waitForVolumeDetach` is documented as a no-op on single-node clusters; this cluster has 3 nodes, so it is active here. If the cluster is ever reduced to a single node, this setting stops providing any protection and the risk reverts to an unbounded, silent hang.
- No ETA exists for a real fix short of the `rbd-nbd` mounter switch (deferred above) or someone getting CVE-2026-23047 backported into 6.18 LTS upstream — re-check the 6.18.y changelog periodically; this is not something Renovate's Talos version bumps will surface.
- `mon_clock_drift_allowed` was temporarily raised to `0.1` live in Ceph config during the incident (to unblock tuppr's `HEALTH_OK` gate on `mon.p`'s persistent ~55-60ms clock drift) and is still set that way — it's a runtime `ceph config set`, not in git. Needs reverting; `ser8b`'s drift itself doesn't have an obvious config cause (TSC clocksource, no instability warnings, identical Cloudflare NTP config across all three nodes) — likely inherent oscillator variance on that unit, with a LAN NTP source as an untested next step. Unrelated to this decision but discovered in the same investigation.
- The community kubeconform schema catalog (`kubernetes-schemas.pages.dev`) doesn't yet include `waitForVolumeDetach` in its `TalosUpgrade` schema as of tuppr 0.5.0 — `task kubernetes:kubeconform` will flag it as an unknown property even though it's valid against the live CRD (confirmed directly against the cluster's installed CRD and the chart's bundled CRD). Don't treat that specific kubeconform failure as a real error; re-check once the catalog catches up.
